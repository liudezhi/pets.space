# 架构与决策

## 决策 001 · 首版按业务边界组织

**状态**　规划采纳，待首个可运行版本验证。首版采用单仓库、按业务划分模块的方式，保持统一构建和发布。多人实时联机和独立微服务会增加运维成本；当某项业务有单独扩容、发布或故障隔离需求时，再根据实测拆分。

| 模块 | 拥有的数据与责任 | 与其他模块的约定 |
| --- | --- | --- |
| 世界与景观 | 地块、地标、朝向、季节和资产版本 | 用稳定的地点编号定位。3D 场景和轻量页读取同一份获准展示的档案。 |
| 纪念档案与媒体 | 纪念编号、地点编号、照片、文字与可见范围 | 永久链接按纪念编号解析；服务端检查访问权后提供照片。更换模型或移动庭院后仍可找到同一份档案。 |
| 献花与礼物 | 收花设置、已放置礼物、赠送记录 | 免费花可独立于交易创建；付费商品从已确认订单取得发放依据；展示时长与保存记录分别管理。 |
| 身份、邀请与交易 | 身份、邀请码、开通权益、订单 | 由服务端确认注册资格、金额和支付结果。按唯一订单处理重试，确保邀请码消耗和对应权益发放一致；重复回调可安全重放。 |
| 保存与恢复 | 导出格式版本、媒体清单和校验值、恢复流程 | 从纪念数据生成通用照片、文字及可离线浏览的页面。恢复时同时核对隐私状态与删除请求，避免已删除内容重新公开。 |

技术候选为 TypeScript、Three.js、关系数据库和对象存储；前端框架、托管服务及支付供应商在对应阶段选定。选型依据包括手机实测、团队维护成本、数据可迁移性。

## 扩展与维护的实测方法

- **加一座庭院。** 用地块描述登记新地点、访问位置和资源清单。保留旧地点编号；若调整坐标，在版本映射中指定新的落点。以旧分享链接检查同一纪念档案、照片和献花。
- **加一种花。** 在礼物目录登记品种、展示素材和获取规则，免费或付费走对应入口。用旧礼物记录验证显示，再用支付重复通知验证新商品仅发放一次。
- **换一代引擎或数据结构。** 存档带格式版本；数据变更提供迁移和恢复步骤，使用一份前一版测试档案演练。固定视角影像和轻量页给旧地点保留可访问的呈现方式。
- **追踪问题。** 记录请求或订单关联编号、资源版本和错误类型；日志示例使用测试资料。涉及支付、权限或格式迁移的改动附能复现相应风险的回归检查。

## 决策 002 · 让河湾在轻量浏览与实时漫游之间切换

2026-11-19 · 风景样板采用 Vite、原生 JavaScript 与 Three.js。文档中的概念图直接作为轻量模式的取景图，避免维护两套副本。三个地点使用相同的地点编号连接取景、URL 片段、地图和漫游落脚点。

页面先提供浏览与纪念册，访客进入漫游时才加载渲染器。场景模块提供地形高度、通行边界与释放资源的方法，控制模块负责相机、输入和帧循环，后续账号或订单逻辑可独立开发。实时模式需要 WebGL 2，启动失败时保留轻量体验。初次实现侧重路线与视线，因此程序化景观与摄影风格参考图仍有明显材质差距。下轮依据真机测量与石前近景对照，再决定资产精度及资源加载策略。

## 决策 003 · 单进程服务验证纪念档案与探访

2026-11-19 · 本轮采用 Node 内置 SQLite，首页、3D、档案 API 和照片通过同一来源提供。开发与打包版本共用同一套中间件，默认仅监听本机，档案库保存在静态文件目录之外。账号、会话、档案和献花分别建表，公开查询与图片读取均在服务端核验可见性。公开目录以独立编号定位每一座花园；「河湾」与「桦坡」作为可复用的场景模板，同一片风景中展示当前探访的宠物。

测试邀请码用于发放试用资格；恢复码和会话在数据库中保存摘要。公开链接只带纪念编号。照片以展示版 WebP 存储，授权后独立返回，避免读取档案文字时捎带图片。建园及送花均支持幂等重试。跨主机扩容、原图长期保存、逐户付费邀请码及运营方身份恢复需要另行落地。

## 决策 004 · 公共步道与家庭庭院共用访问规则

2026-11-19 · 新园领取稳定的地块序号，步道每六块一组。设为私密后移出公开查询，其余石位保留。3D 在靠近和打开档案时重新读取授权信息，退出漫游时释放照片、绘图资源和事件监听。家庭庭院通过关联表收纳同一园主的伙伴，访客读取经过可见性筛选的成员。跨家庭交接会撤销原归属，并把花园转为私密。

园区时钟采用北京时间和北半球季节。同一时段共享确定性的天气，各设备可单独预览季节、时段和天气。地形、天象、植被、环境音、街区交互各自管理场景资源，档案和订单接口独立于 WebGL。浏览器缺少 WebGL 时，轻量图片与纪念页仍可通过网页服务访问。

## 决策 005 · 由订单发放权益

2026-11-19 · 免费献花单独记账；建园、庭院、花束和花瓶使用统一的商品、订单与发放记录。展示与计价共用 `shared/catalogue.mjs`，服务端把下单时的价格固化在订单内。默认沙盒支持中断后继续结算，Stripe 托管模式仅通过核验后的服务端通知确认收款。支付结果、订单展示状态和已发权益分别记录，以便重放和检查。目标花园关闭送礼等情况下，已收款订单进入人工复核。真实商户、退款执行与对账责任见[运行与百年保存](运行与百年保存.md)。

## 决策 006 · 可带走的档案及可验证的恢复

2026-11-19 · 数据库分别存放展示图和自愿保留的原件。公开园中的每一张相册图仍受自己的授权控制。园主导出的 HTML 嵌入照片、原件、固定风景、园址、回忆和探访记录，内含可单独下载的 JSON 与原图 SHA-256。场景版本 `riverbend-1` 及稳定地块号写入档案；以后更换引擎时可从这份记录回到旧园址。原件和私人寄语只随园主导出，示例麦子的虚构档案另行开放。

运营备份通过 SQLite 一致性快照读取已提交的数据，校验清单包含版本、大小与摘要。恢复在独立目录验证完整性和外键。回切之前仍须核对备份后的删除与撤回记录。家庭交接、离线导出、运营备份分别解决换维护人、家庭留存和整站故障三种问题。

## 决策 007 · 按步行与驻足分配渲染开销

2026-11-19 · `walk-quality.js` 根据一段时间内的帧耗选择移动时的像素预算与细节档位，`walk.js` 负责输入和画布尺寸。各场景模块处理自身的几何、材质与可见范围。地形档位共用顶点、岸线与碰撞高度；公开碑体合批后的拾取编号与当前可访问的档案同步更新。这样同一条路在不同档位都有相同的落脚点和探访对象。

弱设备行走时会看到分辨率较低的水面与远景；自动模式驻足后恢复清晰，精细模式保留原生画幅。调整预算时用固定路线和真实时间各测一轮，另在同一石前机位检查降档前后恢复的完整像素。后续取得目标手机和硬件加速电脑的测量后，再据此调整预算。[实测与复测命令](../design-qa.md)
