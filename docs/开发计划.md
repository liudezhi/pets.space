## 首个迭代的实施顺序

1. **定景。** 景观设计交北向机位草图和同一河湾的三张视图。产品负责人根据石前照片是否清楚、能否认出回程地标、这里适合哪只宠物来选择方向。
2. **走路。** 开发用简单地形打通「入口望树 → 河湾石前 → 过桥回望」，同时建立可复现的安装与构建步骤。美术按约定朝向和比例细化石前最后三米。使用有来源记录的示例素材。
3. **合并验收。** 测试记录桌面步行、手机直达和轻量阅读的实际表现。请体验者指出想停下的地方并说说原因，产品负责人据此决定需要修改的机位或动线。

## 协作与日常记录

产品负责人决定风景取向、收费权益和保存承诺；体验设计负责访问路径；景观美术负责场景；架构与开发负责实现；测试负责独立验证；运营与档案保管负责上线后的持续服务。早期可一人兼任多个角色，涉及百年经费或机构接续的决定由实际运营责任人确认。

每项工作开工前写下使用者、目标和一个可观察的验收结果。实现后在同一提交或合并请求中更新受影响的文档。产品规则改在产品记录，跨模块取舍写入架构决策；每个可交付结果、失败验证或阻塞写入开发记录，附复查方法。常规逐行改动由 Git 历史追踪。

首个可运行版本需要锁定依赖版本，提供一条构建命令和覆盖关键路径的检查。从干净检出执行一次，记录真实结果。公开部署、真实收费和把测试数据换成用户资料，分别记录启用时间、责任人及回退办法。
